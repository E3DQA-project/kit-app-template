# Why does the DualShock 4 right stick jitter or appear to reverse in E3DQA Scene Viewer?

**Question:** In `nycu.e3dqa_scene_viewer`, why can the DS4 right stick (camera look) jitter or appear to move the camera in the opposite direction, and is the controller faulty?

**Answer:** The active app delegates DS4 input to Kit's `omni.kit.manipulator.camera`. The installed Kit default maps the right stick to `look` with a `0.10` dead-zone and `0.75` scale; E3DQA overrides that dead-zone to `0.20`. The reported full-deflection failure was caused by Kit re-scaling a retained right-stick component when only the other axis changed:

- `camera_controls` starts with the E3DQA viewer and writes `/persistent/exts/omni.kit.manipulator.camera/lookSpeed/0 = -180.0` on every startup (and when its preset is reapplied).
- Kit applies `lookSpeed` to gamepad look as well as mouse look, so the horizontal right-stick axis is deliberately inverted.
- This inversion was added to compensate for Matrix-3D's camera-image convention and the 180-degree local roll applied to the initial `/BrowserCamera` pose. It is a global input-axis change, not a DS4 calibration.

With E3DQA's negative horizontal speed, the repeated scaling flipped the yaw command's sign. With its half-speed vertical setting, repeated scaling drove the pitch command toward zero. The behavior did not require a defective controller.

**Applied remediation:** `camera_controls.gamepad_fix` undoes the previous scaling before Kit reuses a look component, so each component is scaled exactly once per event. This preserves the chosen camera mapping and speed. The user confirmed that full left, right, up, and down deflection now all work normally in the relaunched viewer.

**Follow-up observation (2026-09-23):** The host exposes the physical DS4 as `/dev/input/js1` (`Sony Computer Entertainment Wireless Controller`). Its centered right-stick axes (Linux joystick axes 3 and 4) repeatedly report small offsets of approximately `-0.03` and `+0.02`, but these are below the E3DQA `0.20` look dead-zone and do not explain a failure only at full deflection. Kit's look path maps those two axes to yaw and pitch respectively; it does not map the right stick to roll. The inspected Kit gamepad/look code has no explicit pitch limit, so a full up/down stop must be investigated as a viewport/camera-manipulator state issue rather than assumed to be a normal pitch clamp. A focused full-left/full-right raw capture remains necessary to determine whether the DS4/driver sends contradictory saturated axis values or whether the remaining horizontal reversal occurs after Kit receives valid input.

**Earlier full-horizontal capture (2026-09-23):** One unsynchronised trace reached `+32767` in a requested direction and only `-12901` in the other. Because the sampling window did not reliably line up with the user's motions, this does **not** establish an asymmetric controller or driver range. It also did not show simultaneous opposite saturated values.

**How to distinguish DS4 from driver failure (2026-09-23):** The device is a wired USB DS4 (`054C:05C4`) using the kernel's in-tree `hid_playstation` driver. A synchronized raw full-range test on another host would be useful only if range asymmetry remains after the Kit fix. A generic joydev calibration tool would not fix the Kit gamepad reuse/scaling error.

**Controller-tester cross-check (2026-09-23):** The user reports that a DS4 controller tester on this same host shows normal behavior. The earlier unsynchronised full-deflection raw capture does not justify replacing the controller or changing the kernel driver. A first synchronized capture using a Cross-button start marker received no matching button event and produced no measurement. The subsequent 15-second timed capture is described below.

**Root cause found in Kit 110.1.0 (2026-09-23):** The previous recommendations to simply make the horizontal `lookSpeed` positive were incomplete. In `gamepad.py`, `GamePadController.__apply_events` reuses `self.__action_modes["look"]`, which already contains values multiplied by `model_speed`. It updates only components present in the latest event, then multiplies *all* components by `model_speed` again. E3DQA's horizontal `lookSpeed/0=-180` becomes a factor of `-1`; when the right stick is held horizontally and a small event arrives on its vertical axis, the retained horizontal command flips sign. The vertical `lookSpeed/1=90` becomes a factor of `0.5`; while held vertically, horizontal-axis events repeatedly halve the retained vertical command. A local reproduction gives horizontal `-1,+1,-1,+1` and vertical `0.5,0.25,0.125,0.0625`, matching the reported jitter/reversal and apparent wall. A synchronized 15-second `/dev/input/js1` capture reached `-32767` on right-stick X and both `+32767` and `-31736` on right-stick Y while the other axis continued reporting events. The precise timed motion sequence was not cleanly aligned, so the raw capture alone does not prove both X directions reach full scale, but it does corroborate the cross-axis event trigger. The same-host controller tester is normal. These findings make the Kit reuse/scaling defect the leading cause; they do not indicate a faulty DS4.

**E3DQA workaround verification:** `camera_controls.gamepad_fix` restores an existing look command to its unscaled value just before Kit processes a new look event. Kit then applies its normal scaling once. This preserves the existing horizontal direction and vertical sensitivity and avoids editing Kit's cached vendor extension. Three focused tests passed; the E3DQA release build succeeded; the live app log confirms the fix installed; and the user confirmed all four full-stick directions work normally.

**Verified against:** live `kit-app-template` tmux session launched as `nycu.e3dqa_scene_viewer.kit` on 2026-09-23; `source/extensions/camera_controls/camera_controls/extension.py`; the active persisted `user.config.json`; and Kit SDK `omni.kit.manipulator.camera-110.1.0+698af100` source/configuration.
