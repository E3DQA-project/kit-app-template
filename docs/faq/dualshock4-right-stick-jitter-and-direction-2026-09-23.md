# Why does the DualShock 4 right stick jitter or appear to reverse in E3DQA Scene Viewer?

**Question:** In `nycu.e3dqa_scene_viewer`, why can the DS4 right stick (camera look) jitter or appear to move the camera in the opposite direction, and is the controller faulty?

**Answer:** The active app delegates DS4 input to Kit's `omni.kit.manipulator.camera`; it has no E3DQA-specific gamepad event handler. The installed Kit default maps the right stick to `look` with a `0.10` dead-zone and `0.75` scale. Therefore a worn stick, wireless/remote-input reconnect, or input values just above `0.10` can produce genuine jitter, but the current software configuration also contains a verified directional issue:

- `camera_controls` starts with the E3DQA viewer and writes `/persistent/exts/omni.kit.manipulator.camera/lookSpeed/0 = -180.0` on every startup (and when its preset is reapplied).
- Kit applies `lookSpeed` to gamepad look as well as mouse look, so the horizontal right-stick axis is deliberately inverted.
- This inversion was added to compensate for Matrix-3D's camera-image convention and the 180-degree local roll applied to the initial `/BrowserCamera` pose. It is a global input-axis change, not a DS4 calibration.

As a result, a consistent horizontal reversal is software-caused. Apparent direction changes at different orientations are also plausible because look is evaluated in the camera's rolled local frame. A raw DS4 axis trace is still required to attribute jitter specifically to hardware: if the untouched right-stick values remain nonzero or change sign outside the configured dead-zone, the controller/connection is contributing; otherwise the camera mapping is responsible.

**Recommended remediation:** Separate dataset camera-pose correction from interactive look input: restore a positive horizontal `lookSpeed`, retain the initial camera's local roll correction, and raise the Kit `gamePad.look.deadZone` (for example, to `0.18`–`0.25`) only if an input trace shows drift. Validate with the physical DS4 by holding the right stick centered, then moving it horizontally at a level initial camera pose and after a rotated view.

**Follow-up observation (2026-09-23):** The host exposes the physical DS4 as `/dev/input/js1` (`Sony Computer Entertainment Wireless Controller`). Its centered right-stick axes (Linux joystick axes 3 and 4) repeatedly report small offsets of approximately `-0.03` and `+0.02`, but these are below the E3DQA `0.20` look dead-zone and do not explain a failure only at full deflection. Kit's look path maps those two axes to yaw and pitch respectively; it does not map the right stick to roll. The inspected Kit gamepad/look code has no explicit pitch limit, so a full up/down stop must be investigated as a viewport/camera-manipulator state issue rather than assumed to be a normal pitch clamp. A focused full-left/full-right raw capture remains necessary to determine whether the DS4/driver sends contradictory saturated axis values or whether the remaining horizontal reversal occurs after Kit receives valid input.

**Focused full-horizontal capture (2026-09-23):** The DS4's raw horizontal right-stick axis is asymmetric before Kit receives it: one requested full direction reached `+32767`, while the opposite direction reached only `-12901` (about 39% of full scale). The perpendicular axis remained near center during this capture. This proves a controller, USB-link, or host-driver calibration/input issue upstream of E3DQA; a dead-zone cannot repair it. The trace did not show simultaneous opposite saturated values, so it alone does not explain an instantaneous direction reversal. The remaining confirmed software-side contributor is E3DQA's globally negative horizontal `lookSpeed`, which should be separated from the dataset camera-pose orientation correction.

**How to distinguish and resolve DS4 vs. driver failure (2026-09-23):** The device is a wired USB DS4 (`054C:05C4`) using the kernel's in-tree `hid_playstation` driver, not a Steam/SDL remapping layer. The raw trace therefore rules out E3DQA and Kit but does not alone distinguish hardware from the kernel driver. Repeat the same full-left/full-right raw-axis trial three times, then test the same controller and USB cable on a second host (or console) with a controller tester. If the asymmetric range follows the controller, repair or replace its right-stick potentiometer/controller; if it occurs only on this host, first try another USB port/cable and a supported kernel update before considering driver regression work. A generic joydev calibration tool is not a reliable solution for E3DQA because Kit consumes its own input path rather than the `jstest` display values. If hardware replacement is not practical, the reliable software workaround is an E3DQA-specific controller input layer: disable Kit's native gamepad camera handler and apply per-direction normalization, dead-zone, saturation, and pitch policy before sending camera look commands. That is a bounded implementation project and must be verified with the physical DS4.

**Controller-tester cross-check (2026-09-23):** The user reports that a DS4 controller tester on this same host shows normal behavior. Treat the earlier unsynchronised full-deflection raw capture as inconclusive for hardware diagnosis; it does not justify replacing the controller or changing the kernel driver. A synchronized raw capture was attempted using a Cross-button start marker but no matching button event was received, so it produced no new measurement. The remaining high-confidence next test is software-scoped: remove E3DQA's global negative horizontal `lookSpeed` while retaining the camera-pose correction, then re-test Kit's native handler. If that does not resolve the full-stick behavior, instrument/replace the native Kit gamepad handler with a calibrated E3DQA input layer.
